# L01: быстрый MID с проверкой адресата и линии

**Готов к native-проверке, не установлен; native/Fitness ещё не пройдены.** Владелец разрешил последующий деплой; текущую серию не прерывать. Предлагаемая пятёрка: GK13 / DEF19 / MID L01 / FWD1v16 / FWD2 stance rev9, формация1-1-2. Это одно изменение MID. P01 отклонён, P02/P03/P04 не добавлять.

## Поведение и пределы

При подтверждённом владении MID: близкий центральный удар по открытой линии; иначе пас свободному FWD1/FWD2 по свободному пути с учётом движения; иначе безопасный возврат DEF. Дальний GROUND допустим только после проверок получателя и линии. Проекция0,35с и геометрические пороги — непроверенные ограничения, не физическая модель полёта. Энергия не запрещает открытый удар или пас в ноги: формула её влияния на точность неизвестна. Спринт, THROUGH и AERIAL не вводятся.

При неизвестном/противоречивом владении, старом кадре, рестарте, чужом мяче или отсутствии безопасного решения — CLEAR_OVERRIDE. Дальше играет встроенный движок, который может двигаться, дриблинговать и терять мяч. Поэтому общий MOVE в отчёте не обязан исчезнуть. Новая оборона MID не реализуется. Это смена исполнения и on-ball политики одной роли, не причинный A/B только модели.

Цели всей пятёрки: GK — надёжный ввод; DEF — страховка центра; MID — выход из давления; FWD1 — завершение открытых моментов; FWD2 — второй адресат и ширина. Выполнение этих целей остальными четырьмя надо проверять эпизодами. Следующий отдельный кандидат DEF/P03 допустим после анализа L01, если подтвердится лишний прессинг/пустой центр.

## Native → установка → Fitness

1. Завершить текущую серию. Сверить портал READY, отсутствие входящего матча, действующее окно и единственного оператора. Сохранить приватный readback пяти bindings, особенно MID15.
2. В отдельном checkout точного research commit собрать/сверить CodeZip. Загрузить в существующий code bucket под отдельным `mid-l01/<sha256>.zip`. Создать отдельный Runtime, не обновляя FWD2 или исходный MID: CodeZip, PYTHON_3_13, main.py, существующая execution role, network PUBLIC, idle900/maxLifetime28800. IAM не расширять. Environment строго PLAYER_ID=2, MID_AUDIT=1, BUILD_COMMIT=<точный source commit>.
3. Дождаться READY; сверить role, code/archive, network/lifecycle/environment. Записать region/runtimeId/runtimeArn/buildCommit в приватный `.local/mid-fast-v1/binding.json`. Пять исходных bindings пока сохраняются.
4. В свободном окне запустить собственные диагностические сессии. Скрипт сверяет фактический загруженный архив, читает весь stream, без retry; останавливает только свои session:

```sh
python3 mid_fast_v1/native_probe.py --binding .local/mid-fast-v1/binding.json --output .local/mid-fast-v1/native.json --apply
python3 mid_fast_v1/grade_native.py .local/mid-fast-v1/native.json --output .local/mid-fast-v1/native-grade.json
```

Без verified deadline grader оставляет gate=false. После проверки официального источника добавить `--deadline-ms <число> --deadline-source <источник>`. Требуется224/224 полных валидных ожидаемых ответа, ноль просрочек, p95≤min(800мс,80%deadline). 800мс — инженерный запас, не правило турнира. Первые и последующие вызовы видны отдельно, медленные первые нельзя выбрасывать. CloudShell path не равен игровому пути. Проверь доступные реальные MID-входы: player2/сторону/владение/координаты; один CLEAR_OVERRIDE не доказывает работу пасов. Недоступное покрытие явно пометь.

5. При native PASS заменить только MID новым Runtime, пройти свежий Fitness5/5 и сверить остальные bindings. При ошибке/неверной роли/просрочке — вернуть MID15 и Fitness, без рейтинговой серии кандидата.
6. После успешных проверок — отдельные пять матчей в игровом потоке на неизменном L01. Fitness проверяет совместимость, не победную тактику. По роли сохранять полную p50/p95, первые/поздние ответы, ошибки и применение; по MID — адресатов, причины fallback, реальные потери и завершённые пасы с явным знаменателем/покрытием. Без traces — null. Итог: W/D/L, голы, моменты, соперники и стороны; обычное поражение не меняет состав посреди блока.
