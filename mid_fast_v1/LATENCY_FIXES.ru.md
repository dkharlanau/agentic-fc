# Исправления проверки задержек — 25 октября 2026

База: `e34247c6000dc910bbe91f575bb261661b1db1b0`. Изменены только
клиентский сбор измерений и офлайн-проверка допуска. Нового Runtime,
изменений AWS, игровых регистраций, промптов, формации или матчей нет.
Это исправление контроля и наблюдаемости, **не доказанное ускорение AWS**.

## Подтверждённый дефект и исправление

Прежний `grade_native.py` печатал `nativeGatePassed: false`, но нормально
завершался с кодом 0. Проверка могла выглядеть успешной для shell/оркестратора,
который смотрит только на exit code. Это не доказательство, что такой дефект
уже привёл к ошибочному релизу, и не причина холодного старта.

Теперь коды завершения: **0 — native PASS; 1 — условия допуска не выполнены;
2 — некорректные входные данные или ошибка файловой операции**. Ошибочный ввод
заменяет старый PASS-отчёт на явный FAIL, когда файл доступен для записи.
Входной файл нельзя использовать как выходной. При невозможности записи
процесс завершается с кодом 2: любой вызывающий процесс обязан проверять его.

Строгие проверки полного ответа, хешей, порядка, всех первых вызовов и p95
сохранены. Первый ответ >1000 мс не скрывается за хорошим общим p95.
`failureReasons` отличает просрочки первого и повторных вызовов, неверный
ответ, неполный план и отсутствие подтверждённого дедлайна.

## Что добавлено в измерения

`native_probe.py` сохраняет один SDK-клиент и один новый session ID на каждую
логическую тестовую сессию; повторные вызовы используют тот же ID, как и раньше.
Здесь не была доказана генерация новой сессии на каждом такте.
Новая телеметрия позволяет обнаружить смену/смешивание IDs, нарушение номера
вызова, несовпадение возвращённого ID, неожиданные повторные попытки SDK и
ошибочный HTTP-статус. Неизвестные сведения остаются `null`.

В отчётах отдельно видны время до возврата SDK с заголовками, время дочитывания
тела, полное время и число первого/повторных вызовов. Это клиентские интервалы:
**они не разделяют сеть, создание microVM и внутренние очереди AWS**.
Стабильный ID не доказывает отсутствие перезапуска серверной среды.

Поток ответа закрывается и при ошибке чтения/UTF-8. Закрытие измеряется за
границей полного ответа и не подменяет его задержку. Наличие ошибки закрытия
не скрывается. Реквизиты собственных probes сохраняются перед первым вызовом;
cleanup останавливает только IDs, созданные данным запуском. Его ошибки
фиксируются. Новые файлы создаются приватными (0600) и заменяются атомарно.

`*.runtime.json` фиксирует readback платформы, версию SDK, хеш архива и план.
В binding можно явно добавить `platformVersion`; несовпадение прервёт probe.
Автоматического выбора платформы, прогрева или дополнительных вызовов нет.

В `.local/` остаются исходные ответы и служебные session IDs для cleanup.
В телеметрии IDs заменены HMAC-псевдонимами с отдельной случайной солью на запуск;
сырые IDs, ARN, request IDs и тексты исключений не попадают в сводный grade.
Старые receipts читаются, но отмечены `sessionTelemetry.status=not_recorded`,
а не представлены как подтверждение правильного жизненного цикла сессии.

## Как использовать

Существующие receipts можно перепроверить без AWS:

```sh
python3 mid_fast_v1/grade_native.py .local/mid-fast-v2/native.json \
  --candidate L02 --deadline-ms 1000 \
  --deadline-source https://agenticfootballcup.com/ \
  --output .local/mid-fast-v2/native-grade.json
```

Не продолжать release при ненулевом exit code; не добавлять `|| true`.
Даже exit 0 здесь означает только прохождение native-проверки, не Fitness,
не подтверждение применения команды движком и не право автоматического релиза.

Не повторять те же 224 вызова только ради новой телеметрии. Сначала игровой
оператор проверяет реальные session IDs, момент начала секундного таймера и
существующие логи медленного матча. Новое измерение допустимо лишь на свободной
границе серии и с записанной различающей гипотезой. `--apply` остаётся обязательным.
Никакие игровые сессии не переиспользуются для probes и не останавливаются ими.

## Следующий различающий эксперимент

Сначала read-only проверить, сохраняется ли ID одной роли между игровыми
тактами и есть ли подготовка именно этой сессии до первого срочного вызова.
Связать роль/такт/версию с началом запроса, входом в обработчик, полным ответом
и доступной отметкой применения. Нет отметки — оставить неизвестной.

Только если движок позволяет заранее запускать будущую игровую сессию,
отдельно проверить этот поддерживаемый путь; прогрев посторонней сессии
не является решением. При медленных повторных вызовах проверять общий путь
доставки/очередь/атрибуцию, а не автоматически обвинять холодный запуск.
Не ослаблять дедлайн и не заменять четыре остальные роли.

## Проверки и откат

Локально выполнены 30 unit-тестов транспорта, диагностик, приватного сохранения
и CLI. Они используют заглушки, не AWS. Дополнительные шесть интеграционных
тестов используют реальный синтетический план из репозитория; полный результат
см. в GitHub Actions конкретного коммита. Никакой синтетический тест не доказывает
ускорение матча. Исходные native-grade тесты сохранены.

Изменённые файлы не входят в `mid_fast_v2/artifact.json`; его архив и политика
не изменены. Откат — вернуть только файлы этого исправления, не трогая результаты
матчей и чужие коммиты. Недопустимо делать reset/force-push всей ветки.

Прочитан coach-v1.0: C01 принят как проверка исполнения; C02/C03 отложены,
поскольку эта правка не изменяет тактику и не запускает серию.
