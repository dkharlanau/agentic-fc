# Запрос игровому потоку — передать после текущей серии

Готовый текст для владельца. Исследовательский поток его никому не отправлял.
Диагностика и очередь по игрокам готовы к рассмотрению; игровые улучшения ещё
не доказаны. P01/P02 и старый 156-request план сохранены без изменения.

---

Заверши текущую базовую пятёрку без смены настроек. На границе серии прочитай
HANDOFF, актуального EXPERT_COACH и COACH_REVIEWS; сделай один общий разбор пяти
матчей. Сверь фактические setup/model/prompt/build, сторону и источники отчётов.
Не считай эту базовую серию тестом P01: кандидат пока не установлен.

Исследование в `codex/model-prompt-lab-20261025`, папка
`research/v3/model-prompt-lab/`: прочитай DECISION_LATENCY.ru.md и PLAYER_UPDATES.ru.md.
Не переноси исследовательский HANDOFF поверх игрового checkpoint. Ветка содержит
готовые diff и офлайн-анализ; её не требуется целиком мержить для проверки P01.

Сначала выгрузи уже существующие точные traces проблемных игр/ролей, если они
доступны в разрешённом доступе. Не меняй IAM, настройки логирования или deployment
ради выгрузки. Приватно свяжи role/side/tick/session с model/build/prompt hash.
В CloudTrail проверь также Runtime data-plane события: отсутствие InvokeHarness
само по себе не означает отсутствия вызовов. Сырые данные только в `.local`.

Отдельно по GK/DEF/MID/FWD1/FWD2 сохрани полное время ответа, модельное время,
токены, число вызовов/повторов, ошибки/fallback и доступные отметки доставки.
Дай p50/p95 и число наблюдений, отдельно первые/повторные обращения, но не исключай
медленные первые из общего итога. Если доступны лишь средние отчёта — так и укажи,
не называй их p95. Установи первичный источник секундного дедлайна и точку отсчёта.

D02 `candidate/harness-route-timing.patch` — подготовленная диагностическая
правка вызывающего probe-скрипта, не агент и не ускорение. Она не установлена;
новые probes допустимы только в отдельно разрешённом пустом окне, если старых
данных недостаточно. Не запускай probe во время матча, не трогай игровые сессии.

Единственный следующий игровой кандидат — P01: одна строка FWD1, прежняя
Nova2Lite и 1-1-2, GK/DEF/MID/FWD2 без изменений. Используй manifest и точный
`candidate/fwd1-shot-priority-v1.patch`. До установки выполни предусмотренный
парный скрининг на одинаковых входах; сохраняй полный ответ, а не первый найденный
JSON-массив. План содержит 24 синтетических + 2 физических входа, 2 промпта,
3 повтора = 156 requests; допускается досрочно отвергнуть при критическом провале,
но неполный план не проходит gate. Вызовы только в разрешённом окне без игр.

Проверить сохранение открытого удара HOME/AWAY, безопасного паса, смену владения,
отсутствие прироста MOVE/CLEAR вместо хороших действий; strict validity100%,
полный p95 не хуже1.10×контроля и абсолютный подтверждённый дедлайн. Если важная
граница таймера/дедлайн неизвестны, не объявляй gate пройденным.

Только после успешного скрининга: точный readback кандидата, native/physical
проверка и свежий Fitness5/5. Затем, при действующем разрешении владельца на
новую серию, пять завершённых рейтинговых матчей на одной конфигурации, без
смены после обычного поражения; один общий разбор в конце. Fitness сам по себе
не доказывает полезность решения или соблюдение дедлайна в игре.

При провале не начинать кандидатную серию. Если кандидат был установлен,
rollback — исходный FWD1v16, model/hash из manifest, свежий Fitness5/5.
P02 (энергия FWD1), P03 (DEF прессинг/страховка), P04 (MID линия паса/возврат)
остаются в очереди; не объединять их с P01, сменой модели, формации или D01.
Зафиксируй решение по каждой роли и верни обезличенные receipts и результаты.
