# Задержки серии11: что действительно измерено

Источник — зафиксированный `ranked-batch-11.json` в исследовательской ветке,
setup `cohort-setup-20261025.json`; [пересчёт и SHA256](results/latency.json).
Это **средние из отчёта за матч**, не распределение вызовов. p95 отдельных
игровых вызовов из десяти средних восстановить нельзя.

Контроль — игры 1/2/4/5/6/8/10: медиана командной средней 572 мс, медиана
объёма 364 команды. Это тоже неоднородные отчёты, а не «доказанно исправный» путь.

| Отчёт | Средняя команды, мс | Команд | GK / DEF / MID / FWD1 / FWD2, мс |
|---|---:|---:|---|
| 3 | 2410 | 230 | 2870 / 2983 / 2548 / 1637 / 1786 |
| 7 | 2277 | 219 | 2933 / 3100 / 2603 / 1675 / 1647 |
| 9 | 1 | 16 | 3 / 2 / 2 / 2 / 2 |
| Контроль: медиана по 7 средним | 572 | 364 | 80 / 87 / 932 / 619 / 786 |

**Наблюдение 3/7:** командные средние в 4,21 и 3,98 раза выше контрольной медианы;
команд на 36,8% и 39,8% меньше. Все роли одновременно выше своих контрольных
медиан. У GK/DEF кратность особенно велика, поскольку несколько контрольных
значений сами равны 1–87 мс; это не измеренный slowdown конкретной модели.

**Наблюдение 9:** команд на 95,6% меньше контрольной медианы, 100% CLEAR,
при этом счёт 2:1 и три удара. CLEAR возвращает управление движку, поэтому голы
при таком отчёте сами по себе не противоречие. Средняя команды 1 мс ниже всех
пяти показанных ролевых 2–3 мс: по этим округлённым числам нельзя восстановить
одинаковую выборку и формулу агрегации. Это повод проверить знаменатели/путь,
а не объявлять реальное ускорение или поломку физического управления.

**Наблюдение атрибуции:** пятая колонка соперника во всех десяти матчах —
70–86 мс, тогда как наша FWD2 по setup детерминированная и показывает 2–1786 мс.
Это совместимо с неверной привязкой роли/стороны в отчёте, общим ожиданием
или разными путями измерения. Само совпадение масштаба времени не доказывает,
чья это колонка. Автоматически менять стороны запрещено методологически.

## Причины: различимые гипотезы, а не установленный диагноз

| Гипотеза | Поддержка / ограничение | Что различит |
|---|---|---|
| Общая очередь, Harness, сериализация/доставка | Одновременный подъём пяти ролей в 3/7 совместим; реальных отметок нет | Одни и те же invocation/role/side/tick: вход, готовность решения, полное тело, получение сервером |
| Ошибка отчётной атрибуции / смешанные пути | Нестабильный масштаб собственной FWD2 и стабильная пятая колонка соперника | Приватная точная связь фактической role session с командой и записью отчёта |
| Fallback, невызванные роли или неполный отчёт9 | 16 CLEAR при 1 мс совместимы; отсутствие вызова не доказано | Попытки, ошибки, fallback, полные ответы и timestamps по тем же запросам |
| Только медленная LLM | Не объясняет конфигурацию FWD2 без модели; фактическая маршрутизация ещё не проверена | Совпадение build/model-call audit с конкретными матчами |
| Cold start, throttle, повторные вызовы, нагрузка AWS | Данных для выбора нет | Метаданные запросов/ошибок/повторов и первичные интервалы |

Локальный поиск обнаружил только bindings первой игры в `.local/ranked-batch-11`;
воспроизводимых invocation traces игр 3/7/9 в доступных локальных источниках нет.
Старые private/public audits других серий не подставляются за эти игры.
AWS и игровой UI в этой работе не опрашивались. Вывод: **корневая причина пока
неидентифицируема по сохранённым данным**, а замена модели не лечит доказанный
источник задержки, потому что такой источник ещё не установлен.

## Временная цепочка и границы диагностического D01

`game tick → dispatch/Harness → model/tools → role entry/choose → сериализация
→ полное тело у получателя → приём/применение сервером → физическое действие`.
Это схема нужных наблюдений, не утверждение о неизвестной внутренней реализации
сервера. Для пяти ролей надо собирать доступные участки раздельно; нельзя считать
отсутствующую стадию нулевой или вычитать несинхронизированные часы разных машин.

[D01](candidate/fwd2-timing.patch) затрагивает только локальный entrypoint
детерминированной FWD2, включается `TRACE_TIMING=1` в отдельно проверяемом билде.
В JSON команды не добавляется ни одного поля. В приватных логах появляются
корреляционный traceId, входной tick/side, настроенный playerId, UTC входа,
монотонное время choose и момент передачи готовой строки генератором.
Существующий computeMs остаётся отдельным. Второе событие появляется только
при возобновлении генератора после yield; его отсутствие не означает отсутствие
отправленной команды. Время возобновления включает работу потребителя.

**Это не network delivery и не server apply.** Эти поля остаются null. SDK
проверен здесь заглушкой только для локальной совместимости; нативный транспорт,
накладные расходы реального логирования и Fitness неизвестны. Для полной
диагностики нужны приватные точные receipts самого вызывающего кода/сервера.
Если сервер не предоставляет отметку применения, полная задержка остаётся unknown.

D01 — альтернативная самостоятельная диагностика, не часть P01. Перед любым
его продвижением также требуются native/readback и свежий Fitness 5/5 на границе
серии. Rollback — исходный FWD2 stance/source931af03/rev9 с проверенным архивом
из `final-setup-20261025.json`; не менять policy, роли или формацию вместе с ним.
Публично экспортировать только псевдонимы, агрегаты и хеши, без сырых состояний,
session/account IDs, ARN или неотредактированных скриншотов.
