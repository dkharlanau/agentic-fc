## Почему первоначально был предложен P01 — историческое обоснование

Наблюдение: текущий FWD1 одновременно содержит «~25 units» и последующее
«close / clear lane». Это проверяемый риск, не доказанная причина живых поражений.
P01 сохраняет исходный формат, модель, историю, инструменты, проверку владения,
координатный контракт и остальные инструкции; меняется одна строка одной роли.

Гипотеза P01: единый приоритет качества удара уменьшит преждевременные SHOOT,
сохранив открытые близкие удары и безопасные пасы. Альтернатива:
модель уже правильно понимает исходный промпт, дополнительные слова не помогают
или подавляют атаку. Поэтому нужны одинаковые входы и положительные проверки,
а не увеличение доли CLEAR ради формального успеха.

Отдельный первый черновик требовал явной команды владельца мяча. Он **отвергнут
до inference**: в двух сохранённых физических входах отсутствуют и
`possessionTeamCode`, и `hasBall` у всех игроков. Такой guard рисковал выключить
атаку. [Структурный аудит](results/input-contract.json) и [отвергнутый diff](rejected/fwd1-current-state-v1.patch)
сохранены. Синтетические fixtures с добавленными полями не заменяют реальный
контракт. Старые PASS в r1-v2/v3 остаются открытым риском, который P01 не обещает исправить.

**Micro остаётся M01 в очереди.** Её p50/p95 модели 259/372 мс в FWD1 selector
ниже Nova2 393,5/507,8 мс, но этот тест уже содержит подсказки выбора. Полный
Harness Micro p95 = 2787,35 мс, максимум 32054 мс. На свободном JSON FWD2
Micro дала только 1/9 пригодных решений. Замена модели в текущем M8 FWD1
не проверена. Не совмещать её с P01 и не возвращать старый R1 только по 20/20:
его отдельный исторический позиционный пилот завершился 1W/4L.

Ни один вариант не доказал 10 мс end-to-end или превосходство в турнире.

## Воспроизведение без сети

Из корня исследовательского worktree, Python 3.10+; внешние пакеты не нужны.
Нужна история Git с указанными commit исходных промптов (shallow clone недостаточен).

```sh
python3 research/v3/model-prompt-lab/lab.py
python3 research/v3/model-prompt-lab/latency_audit.py
python3 research/v3/model-prompt-lab/prepare.py
python3 -m unittest discover -s research/v3/model-prompt-lab -p 'test_*.py' -v
git apply --check research/v3/model-prompt-lab/candidate/fwd1-shot-priority-v1.patch
git apply --check research/v3/model-prompt-lab/candidate/fwd2-timing.patch
```

Здесь `git apply --check` только проверяет применимость. Скрипты не вызывают
модели, не подключаются к AWS и не применяют patch. Повторный запуск даёт те же
JSON/Markdown. Источники и SHA256 записаны в comparison/latency JSON; хеши старых
промптов сверяются с Git, сохранённые строгие ошибки пересчитываются без ослабления.

Архивный план P01 baseline/candidate теста (не повторять без нового решения после разбора провала): **24 синтетических + 2 физических
FWD1 входа × 2 промпта × 3 повторения = 156 запросов**, чередование промптов. Это только
план, не разрешение исполнять все запросы во время живых игр. Сначала можно
остановить скрининг на первом критическом провале; неполный набор не проходит gate.

```sh
python3 research/v3/model-prompt-lab/candidate_check.py --plan .local/model-prompt-lab/p01-plan.json
python3 research/v3/model-prompt-lab/candidate_check.py --receipts .local/model-prompt-lab/p01-receipts.json --output research/v3/model-prompt-lab/results/p01-new-evidence.json
```

Второй вызов требует реально собранных receipts; сейчас такого файла нет.
Каждая запись: `key`, `modelId`, `requestSha256` из плана, `responseText` —
полный текст ответа, `requestWallMs` — реально измеренное время до полного тела,
`complete` — завершён ли ответ. Не использовать время первого токена.
Ошибочный/незавершённый ответ сохранить с `complete:false`, пустым текстом
и фактическим временем ожидания; не исключать его из выборки. Дубликаты,
неизвестные ключи, другой запрос/модель и отрицательные времена отвергаются.
У двух физических входов проверяется только контракт, качество решения остаётся
null: нет независимой правильной команды для этих кадров. Сырые запросы/ответы остаются в `.local`; публичный результат содержит только
числа, ошибки, псевдонимы и хеши. Ответы и критерии не подмешиваются в model messages.

Офлайн-gate: полный набор, 100% команд по схеме, ноль нарушений ожидаемого
владения/действий, отсутствие ухудшения по каждому случаю и p95 полного
ответа не выше 1,10 baseline. Это выбранный исследовательский порог, не правило
турнира. Дополнительно — ноль выявленных рисков адресата/линии паса и ни одного
опоздавшего/незавершённого ответа кандидата относительно независимо проверенного
дедлайна. В команду оценки добавить `--deadline-ms` и `--deadline-source` с
фактическим значением и ссылкой на подтверждение; здесь значение не задано.
Без них можно получить диагностику, но offline-gate останется false.
Далее независимые native проверки, точный readback, **свежий Fitness 5/5**,
и только затем решение о неизменной серии. Даже успешный offline-gate оставляет
`eligibleForRankedPromotion:false`, пока внешние проверки не подтверждены.

## Запрос, который владелец может передать игровому потоку

> Рассмотри P01 из codex/model-prompt-lab-20261025: только FWD1 prompt
> candidate/fwd1-shot-priority-v1.patch, Nova2Lite/остальные четыре роли/1-1-2
> без изменений. Не применять в текущей серии. На границе серии сначала
> проверь baseline hash и выполни отдельный одинаковый baseline/candidate
> скрининг по candidate_check.py в разрешённом окне без активного матча.
> При провале — остановить кандидат. При успехе — native/readback и свежий
> Fitness 5/5 до допуска к рейтинговому пилоту. Никаких Micro, формации или
> D01 вместе с P01. Сохрани точный rollback исходного FWD1v16, тот же modelId
> и baseline prompt hash из manifest. Размер живого блока возьми из моего
> актуального указания; внутри блока не менять setup. После блока сравни
> очки/голы, исчезновение атаки, безопасные решения и задержку по реальным
> вызовам; обычное поражение не повод менять конфигурацию посреди серии.

Откат при неправильном игроке/стороне, незаконной команде или провале Fitness:
исходный FWD1v16 с сохранёнными настройками и хешем промпта, затем Fitness.
Потеря положительных ударов/пасов в офлайн-тесте также отвергает P01 до игры.
После обычной полной серии отсутствие выигрыша по результатам или ухудшение
атаки — основание не принимать кандидат; разные соперники требуют повторения,
а не причинного вывода из одной малой выборки.
